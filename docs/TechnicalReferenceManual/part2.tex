\section{외부 라이브러리}
\label{section:dirstructure-devenv}

\begin{itemize}
  \item \textbf{Python} \simulator \는 2023년 말 출시되어 현재 가장 널리 쓰이는 버전 중 하나인 \texttt{Python 3.12}\cite{python312}를 사용한다.
  \item \textbf{EnergyPlus} \simulator 에서 EnergyPlus 실행파일 변환 및 실행을 담당하는 idragon 모듈은 2024년 9월 말에 출시된 \texttt{EnergyPlus 24.2}\cite{energyplus242} 버전에 맞추어 개발되었다.
\end{itemize}


\section{기술문서}
\label{section:dirstructure-documentation}

\begin{itemize}
  \item \textbf{Technical Reference Manual} 본 문서.
  \item \textbf{Regression Test Report} Regression Test Report는 소프트웨어의 기능 추가나 코드 수정, 혹은 종속 라이브러리의 업데이트가 기존에 정상적으로 작동하던 기능에 의도치 않은 오류(Regression)를 유발하지 않았음을 검증하고 기록한 문서이다\cite{sommerville2015software}. 이 보고서에서는 표준 테스트용 시뮬레이션을 수행한 결과값, 실행 속도 등을 정량적으로 제시하므로, 이전 버전과 현재 버전 간의 차이를 비교, 엔진의 수치적 정합성과 시스템 안정성을 확인 가능하다.
  \item \textbf{Release Note} \simulator 의 버전별 호환성 등 버전 관리 규칙을 명세하고, 각 버전별 업데이트 내용을 추가, 변경, 수정, 제거 4가지 항목으로 구분하여 기술한다.
\end{itemize}


\chapter{실행 방법}

\simulator\은 아래 세 가지 방법으로 실행할 수 있다.
\begin{itemize}
  \item \textbf{명령줄 인터페이스 (Command Line Interface; CLI)}: EPlusSimpleCLI 실행파일을 이용, cmd 콘솔 명령어로 \simulator 의 주요 기능을 실행한다. GUI 프로그램 등, 본 엔진과 연동되는 외부 프로그램에 권장되는 방법이다. 포맷 변환, DB 조회 등 외부 프로그램과의 연동이 필요한 기능들이 지원된다.
  \item \textbf{Excel 기반 입력파일 실행}: Excel 기반 입력파일(\texttt{.xlsx} 확장자)을 작성하여, 내장 GUI (EPlusSimpleLauncher.exe)를 통해 \simulator \를 실행한다. 본 엔진을 독립적으로 사용하는 사용자에게 권장되는 방법이며, 시뮬레이션의 실행만 가능하다.
  \item \textbf{Python 모듈 직접 사용}: 엔진에 포함된 portable Python, 또는 별도의 환경에서 \pymodule\을 직접 import하여 \simulator 의 모든 함수를 활용할 수 있다. 본 엔진을 parametric 시뮬레이션 등 변칙적으로 활용하려는 연구자 및 개발자에게 권장되는 방법이다. 단, EnergyPlus 엔진, 기상데이터와의 상대경로가 유지되거나, 별도로 처리해주어야 한다.
\end{itemize}


\section{명령줄 인터페이스 (CLI)}
\label{section:howtorun-cli}

\simulator\은 명령행 인터페이스(Command-Line Interface, CLI)를 통해 실행할 수 있으며, 배포 패키지에는 이를 위한 실행파일 \inlinecode{EPlusSimpleCLI.exe}가 포함되어 있다. 스크립트는 내부적으로 \simulator 에 포함된 Python을 이용, epsimple 모듈을 실행한다 즉, 아래 CLI signature는 \inlinecode{runtime/PythonV3-12-7/python.exe -m epsimple <command> [args]}와 동일하며, 외부 연동 시 안정성을 위해 Python의 직접 호출보다는 CLI 실행파일을 이용하는 것이 권장된다.

\begin{codeblock}{CLI command signature}
EPlusSimpleCLI <command> [args]
\end{codeblock}

여기서 \inlinecode{<command>}는 시뮬레이션 실행 (\texttt{run}: \ref{subsection:clisubcommands-run}), 포맷 변환(\texttt{convert}: \ref{subsection:clisubcommands-convert}) 두 가지가 지원된다.

\subsection{시뮬레이션 실행}
\label{subsection:clisubcommands-run}

\simulator 의 핵심 기능으로, 입력파일을 받아 시뮬레이션을 실행하고, 결과를 출력파일로 저장하는 기능이다. 입력파일은 \texttt{grm}(JSON 형식, \ref{section:format-explanation-grm}) 또는 \texttt{xlsx} (\simulator\ 전용 엑셀 입력 형식, \ref{section:format-explanation-xlsx}) 모두 가능하며, 출력파일은 \texttt{grr}(JSON 형식, \ref{section:format-explanation-grr})이다.

\begin{codeblock}{CLI subcommand signature: `run'}
EPlusSimpleCLI run --input <input_filepath> [--output <output_filepath>]
\end{codeblock}

\paragraph{입력 인자}
\begin{description}
  \item[\texttt{-i}, \texttt{--input}] 입력파일의 경로. \texttt{grm} 또는 \texttt{xlsx} 형식의 파일이 가능하다. 입력파일의 형식은 확장자에 따라 \texttt{xlsx} 확장자는 Excel 기반 입력파일로, 그 외는 JSON 형식의 입력파일로 인식된다.
  \item[\texttt{-o}, \texttt{--output}] 출력파일의 경로. 지정하지 않으면 입력파일의 경로에서 확장자만 \texttt{grr}로 바꾼 경로에 저장된다.
\end{description}

\subsection{포맷 변환}
\label{subsection:clisubcommands-convert}

입력파일의 형식을 변환하는 기능이다. \simulator 에서 입력파일은 \texttt{xlsx} $\rightarrow$ \texttt{grm} $\rightarrow$ \texttt{idf} 순으로 변환되어 시뮬레이션되므로, \texttt{xlsx} $\rightarrow$ \texttt{idf}를 포함하여 3가지 변환이 가능하다.

\begin{codeblock}{CLI subcommand signature: `convert'}
EPlusSimpleCLI convert <input_filepath> --source <input_type> --destination <output_type> [--output_filepath <output_filepath>]
\end{codeblock}

\paragraph{입력 인자}
\begin{description}
  \item[\texttt{input\_filepath}] 변환할 입력파일의 경로. \texttt{grm} 또는 \texttt{xlsx} 형식의 파일이 가능하다.
  \item[\texttt{-s}, \texttt{--source}] 입력파일의 형식. 실제 형식에 맞게 \texttt{excel}, \texttt{json} 중 하나를 지정할 수 있다.
  \item[\texttt{-d}, \texttt{--destination}] 출력파일의 형식. \texttt{json}(입력파일의 형식이 \texttt{excel}인 경우) 또는 \texttt{idf} 중 하나를 지정할 수 있다.
  \item[\texttt{-o}, \texttt{--output\_filepath}] 출력파일의 경로. 지정하지 않으면 입력파일의 경로에서 확장자만 변경된 경로에 저장된다.
\end{description}

\section{Excel 기반 입력파일의 실행 방법}
\label{section:howtorun-excellauncher}

배치 스크립트 \inlinecode{EPlusSimpleLauncher.exe}를 실행하면, 자체 window가 실행된다 (내부서버 실행에 시간이 소요될 수 있음). Excel 기반 입력파일(\texttt{.xlsx} 확장자)을 업로드하여 \simulator \를 실행할 수 있다. GUI는 입력파일의 형식이 올바른지 검증한 뒤, 시뮬레이션을 실행하고, 결과를 레포트 형식으로 제공한다.

웹 기반 GUI는 최대 10개의 리모델링 이후 모델을 동시에 업로드, 시뮬레이션 및 비교할 수 있으며, 최대 4개 코어를 활용하는 병렬 시뮬레이션을 지원한다.


\section{Python 모듈(\pymodule) 직접 사용법}
\label{section:howtorun-pythonmodule}

\pymodule 의 주요 함수는 \texttt{/src/epsimple/api.py}에 정의되어있으며, \pymodule 을 import하여 사용이 가능하다. 주요 함수 및 입력 인자는 \ref{section:howtorun-cli}에서 기술한 CLI와 유사하다.

\begin{codeblock}{Python module API example}

  run_grexcel        ,

run_grjson(

\chapter{입력 및 출력 파일 명세}

\section{입력파일 (grm)}
\label{section:format-explanation-grm}

\simulator 의 입력파일은 실제 건물의 물리적 구성 관계를 반영하여 계층적으로 구성되어 있다. 즉, 건물(\texttt{building})의 하위에 층(\texttt{floor}), 실(\texttt{zone}), 면(\texttt{surface}), 개구부(\texttt{fenestration}) 등과 같은 공간 요소가 실제 건물의 포함 관계와 유사한 형태로 단계적으로 조직된다. 이러한 구조를 통해 건물의 공간적 구성과 시스템 연결 관계를 직관적으로 표현할 수 있다.

한편, 재료(\texttt{material})나 구조체(\texttt{construction})과 같은 물리적 속성은 공간 객체 내부에 직접 중복 정의되지 않고 별도의 객체로 정의된 뒤 참조 방식으로 연결된다. 예를 들어 면(\texttt{surface})은 특정 구조체(\texttt{surface\_construction})를 참조하는 방식으로 구성된다. 이러한 구조는 동일한 정보를 여러 객체에서 재사용할 수 있도록 한다. 또한, 용도프로필과 설비 시스템은 건물 객체와 같은 단계의 \texttt{resources} 아래에 정의되어, 공간 요소와는 독립적으로 구성되며, 필요한 경우 식별자를 통해 공간 요소와 연결된다. 따라서 입력파일의 최상위 객체는 \texttt{building}과 \texttt{resources}로 구성된다.

\subsection{규칙}

\subsubsection{변수의 명칭 관련}

\paragraph{사용가능한 문자} 모든 변수의 명칭은 영문 소문자 및 밑줄(\_)로만 구성한다.

\paragraph{복수형과 단수형} 복수 객체 \texttt{array}를 담는 변수의 명칭(예: ``floors") 또는 복수 객체를 담는 하위 분류를 사용하는 변수의 명칭(예: ``profile\_components"), 길이는 복수형을 사용하며, 단일 값을 담는 변수의 명칭(예: ``name")은 단수형을 사용한다. 단, 길이가 정해져있거나 각 위치별 의미가 명시적으로 다른 \texttt{array}를 담는 변수의 명칭(예: ``vintage")은 단수형을 사용한다.

\paragraph{축약형의 사용} 모든 변수의 명칭은 축약형을 사용하지 않는 것을 원칙으로 하되, 약어 자체로 통용되는 경우(예: ``cop\_heating")에는 축약형을 사용한다.

\subsubsection{ID 기반 객체 참조 관련} \label{subsubsection:ioref:id_description}
grjson에서 다른 객체의 지칭은 \texttt{ID}값에 기반하여 이루어지며, 모든 객체의 이름(``name")은 사용자 편의를 위한 이름으로 실제 데이터 변환 과정에서 사용되지 않는다.

\paragraph{사용가능한 문자} 모든 ID는 영문 대소문자, 숫자, 하이픈(-), 밑줄(\_)로만 구성되며, 숫자, 하이픈(-) 또는 밑줄(\_)로 시작하지 않는다.

\paragraph{ID의 중복} 동일한 \texttt{ID}는 같은 \texttt{class}의 객체끼리 공유할 수 없다. 공급설비와 생산설비는 각각 설비 종류가 다르더라도 같은 목록 안에서 서로 다른 \texttt{ID}를 사용한다. 태양광패널과 풍력발전기도 서로 다른 \texttt{ID}를 사용한다. (모든 \texttt{class}에 대하여 서로 다른 \texttt{ID} 사용을 권장)

\paragraph{예약 식별자} 기본 제공되는 용도프로필과 특수 구조체는 ``@''로 시작하는 예약 식별자로 참조한다. 예를 들어 \texttt{profile\_id}의 ``@소규모사무실''은 기본 제공 용도프로필을, \texttt{construction\_id}의 ``@vintage\_regulation''은 허가일자에 따른 법규 구조체를 의미한다. 사용자 정의 객체의 \texttt{id}에는 예약 식별자를 사용하지 않는다.

모든 변수의 유효성은 필수 및 조건부 사용 여부에 따라 변수(의 속성) 값 존재의 유효성을 검사한 뒤, 타입 및 범위(또는 열거형 상수) 만족 여부를 검사하여 확인할 수 있다.

\paragraph{타입} 모든 변수는 정해진 타입의 변수여야 한다. 모든 변수의 타입은 문자\TypeTag{S}($String$), 실수\TypeTag{F}($Float$), 정수\TypeTag{I}($Integer$), 열거형\TypeTag{E}($Enum$), 불리언\TypeTag{B} 로 구분할 수 있다. 

\paragraph{필수 여부} 입력되지 않을 경우 에러가 발생하는 필수 변수\ReqTag{R}($Required$)와 달리, 비 필수 변수\ReqTag{O}($Optional$)는 미 입력 시 기본값이 사용된다. 변수의 생략과 \texttt{null} 입력은 구분하며, \texttt{null}은 개별 변수의 명세에서 허용한 경우에만 입력한다. 필수 변수라도 \texttt{null}을 허용하는 경우에는 변수 자체는 입력하여야 한다. 객체 및 배열에 항목이 없는 경우에도 필수 변수는 각각 \texttt{\{\}} 또는 \texttt{[]}로 입력하며, 하위 필수 속성은 개별 명세에 따라 유지한다.

\paragraph{조건부 사용 여부} 어떤 변수는 다른 변수(주로 \texttt{type})의 값에 따라 조건부로 사용된다. 이 경우에도 해당 조건에서 필수적으로 요구되는 변수\ReqTag{CR}($Conditional Required$)와 그렇지 않은 변수\ReqTag{CO}($Conditional Optional$)로 구분할 수 있다. 조건에 만족하지 않는 경우, 해당 변수는 json에서 생략될 수 있다.

\paragraph{범위 및 열거형 상수} array면 길이 제약 따짐.
실수\TypeTag{F} 및 정수\TypeTag{I} 타입의 변수는 Python 부동소수점 및 정수 형식에서 표현 가능한 범위 내에서 처리된다.

\paragraph{construction\_id (구조체 식별자)} 구조체 ID. 사용자 정의 구조체는 \texttt{resources.surface\_constructions}의 \texttt{id}로 참조한다. ``@open''은 두 존 사이의 열린 경계, ``@vintage\_regulation''은 건물 허가일자에 따른 법규 구조체, ``@current\_regulation''은 실행일 기준 법규 구조체를 적용한다. 법규 구조체는 면의 유형, 경계조건, 기후지역, 공동주택 여부 및 바닥난방 적용 여부에 따라 결정된다. 다른 존에 접한 벽체는 법규 구조체 대신 기본 내벽 구조체를 적용한다. 변수 생략 또는 \texttt{null} 입력은 허용되지 않는다.

\subsubsection{fenestration (개구부)} \label{subsubsection:ioref:fenestration} 개구부. 벽체의 열린 부분을 의미하며, 창, 문(유리문, 방화문 등) 등 외기와의 접촉 또는 채광·환기를 목적으로 설치된 요소를 포함한다. 경계조건(bounadry\_condition)이 ``outdoors'' 또는 ``zone'' 인 경우에만 사용 가능하다 (``ground'' 또는 ``adiabatic''인 경우, 빈 리스트로 입력하여야 함). 또한 특정 면에 종속된 개구부 면적의 총 합은 해당 면의 면적 합보다 작아야 한다.

\section{출력파일 (grr)}
\label{section:format-explanation-grr}

GRR 파일은 시뮬레이션 수행 결과를 저장하기 위한 데이터 구조로, 건물의 에너지 사용량 및 이를 기반으로 계산된 다양한 성능 지표를 포함한다. GRM 파일이 건물 모델과 시뮬레이션 입력 정보를 정의하는 역할을 하는 반면, GRR 파일은 시뮬레이션 결과 데이터를 체계적으로 저장하고 후속 분석이나 보고서 생성에 활용하기 위한 목적으로 생성된다. 데이터 형식은 JSON 기반 구조를 따르며, 건물 기본 정보, 계산에 사용되는 변환계수, 용도별 에너지 사용량, 그리고 집계된 성능 지표로 구성된다.

GRR 데이터의 최상위 구조는 다음과 같은 주요 객체로 구성된다.

\begin{itemize}
\item \texttt{building} : 건물의 기본 정보
\item \texttt{constants} : 에너지 변환계수 및 비용계수
\item \texttt{site\_uses} : 용도별 연료 에너지 사용량
\item \texttt{source\_uses} : 1차 에너지 기준 사용량
\item \texttt{co2} : 온실가스 배출량
\item \texttt{cost} : 에너지 비용
\item \texttt{summary\_per\_area} : 면적당 성능 지표
\item \texttt{summary\_gross} : 건물 전체 기준 성능 지표
\end{itemize}

\subsection{class별 명세}

\subsubsection{건물 정보}

\texttt{building} 객체는 결과 계산에 사용된 바닥면적(\texttt{total\_area}, $m^2$)을 저장한다. 바닥면적은 모든 존에 포함된 바닥면의 면적 합계이다.

\subsubsection{변환계수 (constants)}

에너지 사용량을 1차 에너지, 온실가스 배출량, 그리고 비용으로 변환하기 위해 사용되는 계수들이 \texttt{constants} 객체에 정의된다.

\begin{verbatim}
constants
 ├─ site2source
 ├─ site2co2
 └─ site2cost
\end{verbatim}

각 항목은 연료 유형(전력:\texttt{electricity}, 천연가스:\texttt{natural\_\allowbreak gas}, LPG:\texttt{lpg}, 유류:\texttt{oil}, 바이오매스:\texttt{biomass}, 지역난방:\texttt{district\_\allowbreak heating}, 지역냉방:\texttt{district\_\allowbreak cooling})별 변환계수를 정의한다.

\begin{itemize}
\item \texttt{site2source} : 에너지소요량[$kWh$]를 1차에너지소요량[$kWh$]로 변환하기 위한 계수
\item \texttt{site2co2} : 에너지소요량[$kWh$]을 온실가스 배출량[$kgCO\textsubscript{2,eq}$]으로 변환하기 위한 계수
\item \texttt{site2cost} : 에너지소요량[$kWh$]을 비용[$KRW$]으로 변환하기 위한 계수
\end{itemize}

\subsubsection{에너지소요량 (site\_uses [$kWh/m^2$])}

에너지소요량은 먼저 용도(end-use) 기준으로 분류되며, 각 용도는 다시 연료 유형별 월별 사용량 배열로 저장된다. 각 배열은 1월부터 12월까지의 면적당 값을 순서대로 포함한다. 사용하지 않는 연료 및 용도도 12개의 0으로 구성된 배열로 저장된다.

\begin{verbatim}
site_uses
 ├─ heating
     ├─ ELECTRICITY     : [12개월 배열]
     ├─ NATURALGAS      : [12개월 배열]
     ├─ LPG             : [12개월 배열]
     ├─ OIL             : [12개월 배열]
     ├─ BIOMASS         : [12개월 배열]
     ├─ DISTRICTHEATING : [12개월 배열]
     └─ DISTRICTCOOLING : [12개월 배열]
       (다른 end-use도 동일)
 ├─ cooling
 ├─ lighting
 ├─ equipment
 ├─ circulation
 ├─ hotwater
 └─ generators
\end{verbatim}

\texttt{equipment}는 실내기기의 에너지 사용량이며, \texttt{circulation}은 팬, 펌프 및 열회수장치의 에너지 사용량을 포함한다.

\texttt{generators}는 건물 내 발전량에서 외부로 송전된 잉여전력을 제외한 자가소비 발전량이며, \texttt{ELECTRICITY}에 0 이상의 값으로 저장된다. 집계 시에는 에너지 사용량에서 차감된다.

\subsubsection{1차에너지소요량 (source\_uses [$kWh/m^2$])}
구조는 에너지소요량과 같다.

\subsubsection{온실가스 배출량 (co2 [$kgCO\textsubscript{2,eq}/m^2$])}
구조는 에너지소요량과 같다.

\subsubsection{에너지 비용 (cost [$KRW/m^2$])}
구조는 에너지소요량과 같다.

\subsubsection{집계: 면적당 (summary\_per\_area)}

각 항목별 연간 합계와 월별 총계를 건물의 바닥면적당 값으로 저장한다. 연료별 및 용도별 항목은 연간 합계인 단일 숫자이며, \texttt{total\_monthly}는 1월부터 12월까지의 월별 총계 배열, \texttt{total\_annual}은 연간 총계인 단일 숫자이다.

\begin{verbatim}
summary_per_area
 ├─ site_uses
     (연료별 집계)
     ├─ ELECTRICITY     
     ├─ NATURALGAS      
     ├─ LPG
     ├─ OIL             
     ├─ BIOMASS
     ├─ DISTRICTHEATING
     └─ DISTRICTCOOLING 
     (end-use별 집계)
     ├─ heating     
     ├─ cooling      
     ├─ lighting
     ├─ equipment
     ├─ circulation
     ├─ hotwater
     └─ generators      
     (합계)
     ├─ total_monthly : [12개월 배열]
     └─ total_annual
 ├─ source_uses
 ├─ co2
 └─ cost
\end{verbatim}

연료별 항목, 용도별 항목 및 총계는 각 지표(\texttt{site\_uses}, \texttt{source\_uses}, \texttt{co2}, \texttt{cost}) 아래에 같은 깊이의 속성으로 저장된다. 연료별 합계와 총계에서는 \texttt{generators}를 차감하며, 용도별 \texttt{generators} 항목 자체에는 자가소비 발전량 또는 이를 변환한 값을 0 이상의 값으로 저장한다.

\subsubsection{집계: 총면적 (summary\_gross)}

구조는 면적당 집계와 같다. 각 값은 면적당 집계에 건물의 바닥면적(\texttt{building.total\_area})을 곱한 건물 전체 기준 값이며, \texttt{site\_uses}와 \texttt{source\_uses}의 단위는 $kWh$, \texttt{co2}의 단위는 $kgCO\textsubscript{2,eq}$, \texttt{cost}의 단위는 $KRW$이다.
